# HF-Access Fabric

Status: architecture and implementation contract, v0.1. Not deployed.

HF-Access is the authenticated device-access layer for the existing Unified Field. It extends the current gateway, node/mesh, orchestrator, task ledger, evidence, and supervision components. It is not a second orchestrator and does not create a parallel device registry.

## Mission

Provide private, auditable connectivity between explicitly authorized HeavenzFire nodes and devices. Start with Windows ZDH, the VM proving ground, and Android A67L; add IoT devices only through owner-authorized enrollment.

## Existing integration points

- Elysium / sovereign gateway: sole externally reachable application entry point.
- Node and mesh: transport and peer connectivity; retain existing topology where verified.
- Brain and orchestrator: task policy, approvals, scheduling, and execution.
- Hash-chained task/evidence ledger: enrollment, authorization, revocation, task, and health events.
- Supervisor / continuity loop: service health, restart, and recovery.

Before implementation, reconcile these paths against the current deployment. The manifest is a historical record, not live health evidence.

## Trust model

1. Every node has a unique cryptographic identity.
2. Enrollment is explicit, time-bounded, and approved by the owner or delegated administrator.
3. Authentication proves device identity; authorization separately decides what that identity may do.
4. Permissions are least-privilege, scoped by device, capability, resource, and expiry.
5. Credentials can be revoked; revocation propagates and is tested.
6. All privileged actions require a policy decision and, where configured, human approval.
7. No default trust from LAN presence, IP address, device name, or agent claims.
8. No secret/private key is committed to GitHub or generated by cloud automation.

## Initial node roles

| Node | Initial role | Default authority |
|---|---|---|
| VM proving ground | Coordination / service host | No production-device authority |
| Windows ZDH | Primary engineering node | Owner-approved development operations |
| Android A67L | Mobile command / worker | Narrow task and status scopes |
| IoT endpoint | Enrolled device | Telemetry-only until separately reviewed |

## Build sequence

1. Inventory and verify the current gateway, mesh, node, orchestrator, ledger, and deployment environments.
2. Select and document the transport integration. Prefer existing private networking and mature TLS/mTLS implementations; do not invent cryptography.
3. Define device identity, enrollment challenge, approval, credential issuance, rotation, and revocation.
4. Implement a durable device registry and append-only audit events using existing ledger/storage interfaces.
5. Add authenticated heartbeat, health state, reconnect backoff, and stale-device handling.
6. Add capability-scoped task routing with deny-by-default authorization.
7. Add IoT adapters one protocol and device class at a time, initially read-only.
8. Test outage, replay, revoked credentials, duplicate enrollment, unauthorized capability, and recovery.
9. Pilot with owned test devices; expand only after independent verification.

## Non-goals / hard boundaries

- No public-internet-wide discovery, scanning, enrollment, or device control.
- No unsolicited connection to third-party devices or networks.
- No unauthenticated shell, generic command execution, or unrestricted proxy.
- No default actuator authority for IoT devices.
- No experimental AI control of medical devices, life-support equipment, safety interlocks, or emergency systems.
- No production secrets, private keys, personal data, or device credentials in repository files.

## Definition of done for v0.1

- An authorized test node enrolls through a one-time, expiring challenge.
- The node authenticates on reconnect using a mature, reviewed transport and a device-specific credential.
- A revoked node is denied on its next authenticated request.
- A node cannot invoke a capability outside its explicit grant.
- Heartbeat loss is detected and recorded without declaring the node healthy.
- A task is accepted, authorized, executed in a bounded test capability, and settled into the existing evidence ledger.
- Tests prove rejection paths as well as successful paths.
- The Windows-to-VM round trip is demonstrated with real endpoint responses and evidence.
- No production IoT device is included in the first acceptance test.

## Current status

This document records the approved design direction only. It does not claim that HF-Access code, credentials, endpoints, or live connectivity exist yet.
